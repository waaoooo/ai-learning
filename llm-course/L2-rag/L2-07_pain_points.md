# L2-07 · 商业化 RAG 痛点分析

> **所属阶段**：L2 RAG 开发实战工坊
> **本课目标**：系统梳理 RAG 商业化落地的 9 类痛点，建立"症状→根因→定位→优化"的诊断框架与 error analysis 方法，为 L2-08/09 的优化方案打底。
> **先修**：L2-01 ~ L2-06（Naive RAG 全链路 + 混合检索）。
> **预计时长**：90-120 分钟（含实验）

---

## 1. 从 Naive 到商业化：差距在哪

Naive RAG 在 demo 里跑得通，是因为：语料干净、问题简单、没有真实用户。上线后面对的是：

- 文档格式混乱（扫描件、表格、多栏）
- 用户问题含糊、口语化、多跳
- 海量文档 + 高并发 + 成本压力
- 合规与可审计要求

于是出现：答非所问、幻觉、引用错误、延迟高、成本高。**本课把问题归类为 9 类痛点，每类给"症状→根因→解决方向→验证方法"。**

---

## 2. 九大痛点（深度版）

### P1. 文档加载准确性和效率
- **症状**：PDF 表格错乱、多栏串行、扫描件无文本、加载慢、乱码
- **根因**：加载器对复杂布局支持差；OCR 质量低；同步阻塞
- **解决**：PyMuPDF / Unstructured / LlamaParse；表格单独抽取；异步批量 + 缓存
- **验证**：抽取后人工抽查表格行列是否对齐；统计加载失败率

### P2. 文档切分粒度
- **症状**：答案被切断 / 上下文冗余 / 检索噪声大
- **根因**：chunk_size 与内容不匹配；固定切分破坏语义边界
- **解决**：递归/结构化/语义分块；父子索引（L2-08）
- **验证**：扫 chunk_size，看 Context Precision/Recall 曲线（L2-11）

### P3. 错排：相关文档排名靠前却是噪声
- **症状**：top-1 不是最佳；真正相关的排在后面
- **根因**：embedding 语义相似 ≠ 任务相关；查询与文档表述差异
- **解决**：cross-encoder reranker（L2-09）
- **验证**：对比加 rerank 前后 top-3 命中率

### P4. 提取上下文与答案无关
- **症状**：检索到的 chunk 跟问题沾边但不含答案
- **根因**：召回粒度粗；查询表述与文档不匹配
- **解决**：查询改写、HyDE、多路召回、父子索引
- **验证**：统计"检索到但答案未使用"的比例

### P5. 格式错误
- **症状**：JSON 解析失败、字段缺失、格式不符
- **根因**：prompt 约束不足；模型能力限制
- **解决**：结构化输出（JSON mode / function calling）、few-shot、校验重试（L2-13）
- **验证**：统计解析成功率，低于阈值就重试或换模型

### P6. 答案不完整
- **症状**：只答了部分，漏掉关键信息
- **根因**：top-k 太小；上下文窗口截断；prompt 未要求完整
- **解决**：增大 k + rerank；Map-Reduce；prompt 要求"完整回答并覆盖所有要点"
- **验证**：与 ground truth 做要点覆盖比对

### P7. 未提取到答案
- **症状**：资料里有答案，但 LLM 说"不知道"
- **根因**：检索未召回；或答案在 chunk 中被稀释
- **解决**：混合检索；更小粒度 chunk；查询扩展
- **验证**：对"应能答"的样本统计拒答率

### P8. 答案太具体或太笼统
- **症状**：过度细节（贴一大段原文）或过度抽象（空话）
- **根因**：prompt 未指定粒度；上下文粒度不匹配
- **解决**：prompt 明确"回答粒度"；多粒度索引；后处理压缩
- **验证**：人工评分粒度适配度

### P9. 幻觉问题
- **症状**：编造事实、引用不存在的来源、数字错误
- **根因**：上下文不足时模型"补全"；prompt 约束弱
- **解决**：严格"仅基于资料"；引用校验；置信度门控；数字保真（L2-10）
- **验证**：Faithfulness 指标（L2-11）

## 3. 诊断框架（按链路定位）

```
加载 → 分块 → embedding → 索引 → 检索 → prompt → 生成 → 输出
  ↑       ↑       ↑       ↑       ↑       ↑       ↑      ↑
  P1      P2      P3/P4   P3     P3/P4/P7 P5/P8  P6/P9  P5/P6
```

**诊断三步**：
1. **看检索**：打印 top-k chunks + 分数；若相关文档不在 top-k → 检索问题（P3/P4/P7）
2. **看上下文**：若相关 chunk 含答案但 LLM 没用 → prompt/生成问题（P6/P9）
3. **看输出**：格式/粒度/数字问题 → P5/P8/P9

---

## 4. Error Analysis 方法

- **建表**：每次查询记录 `query / retrieved chunks / scores / answer / 期望 / 问题类型`
- **分类**：把 bad case 归入 9 类
- **优先级**：按出现频率 × 影响排序，先修高频高影响的
- **回归**：修完后用评测集验证（L2-11）

## 7. 小结

- 商业化 RAG 的问题多来自链路各环节；**先诊断再优化**。
- 9 类痛点对应 Advanced RAG 优化技术（L2-08~L2-09）。
- 评测集 + error analysis 是持续改进的基础（L2-11）。

## 8. 自测题

1. "检索到了相关 chunk 但 LLM 答非所问"可能的原因有哪些？
2. 幻觉在 RAG 中的主要来源是什么？如何缓解？
3. 为什么 chunk_size 会影响"答案不完整"？
4. 你如何系统性地诊断一个 RAG 系统？（步骤）
5. 如何区分"检索问题"与"生成问题"？

### 自测题答案

1. **答非所问原因**：chunk 粒度不当（答案被稀释）、prompt 约束不足、模型注意力分散、top-k 混入噪声、查询表述与文档差异。
2. **幻觉来源与缓解**：来源是上下文不足时模型补全、检索噪声、prompt 弱；缓解用"仅基于资料"+引用校验+置信度门控+rerank。
3. **chunk_size 影响**：过大稀释关键信息、易被截断；过小切断完整答案。
4. **系统诊断步骤**：建评测集 → 记录检索/分数/答案 → 按链路定位 → 归类 9 类 → 优化 → 回归。
5. **区分检索 vs 生成**：看 top-k 是否包含正确 chunk——包含则是生成问题（prompt/模型），不包含则是检索问题（召回/排序）。
