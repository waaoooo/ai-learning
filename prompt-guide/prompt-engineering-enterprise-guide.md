# 提示工程企业实战指南

> 基于 DAIR.AI《Prompt Engineering Guide》(promptingguide.ai/zh) 学习整理，过滤掉学术 noise，保留可落地的企业实践内容。  
> 目标：掌握提示工程并具备企业级实践能力。

---

## 0. 导读

**提示工程（Prompt Engineering）** 不只是写 prompt，而是与 LLM 交互、设计、优化、对接外部工具与保障安全的整套技能。企业级实践的核心：**可控、可复现、可评估、可迭代**。

**学习路径（建议顺序）**
1. 基础（§1-§2）→ 2. 技术选型（§3）→ 3. Agent 与上下文工程（§4）→ 4. 企业案例（§5）→ 5. 风险安全（§6）→ 6. 流程模板（§8）→ 7. 评估（§9）

**企业实践的三条铁律**
- **具体 > 聪明**：直接、明确、可验证，避免模糊。
- **要做什么，不说不做什么**：聚焦期望输出。
- **分解 > 一次性**：复杂任务拆成子任务链，逐步构建。

## 1. 基础：LLM 设置与提示词要素

### 1.1 模型参数（生产必调）

| 参数 | 作用 | 生产建议 |
|---|---|---|
| temperature | 输出随机性 | QA/事实任务 0.0-0.3；创意 0.7-1.0 |
| top_p | 核采样 | 与 temperature 二选一调整 |
| max_length | 最大 token | 控成本与长度 |
| stop sequences | 停止符 | 控制结构（如列表不超过 N 项） |
| frequency/presence penalty | 降重复 | 二选一调整 |

> 原则：temperature 与 top_p 只调一个；frequency 与 presence penalty 只调一个。

### 1.2 提示词四要素

- **指令**：要执行的特定任务
- **上下文**：外部信息/背景，引导响应
- **输入数据**：用户输入或问题
- **输出指示**：输出类型/格式

不是所有要素都必须，按任务类型裁剪。生产中建议显式给出输出格式（JSON/XML/列表）。

### 1.3 三种角色（Chat 模型）

- `system`：设定整体行为与约束（生产必用）
- `user`：用户输入
- `assistant`：模型回复/示例

生产中 system prompt 是行为锚点；user prompt 携带每次请求。

## 2. 提示设计通用原则

1. **从简单开始，迭代**：先简单 prompt，逐步加元素与上下文。
2. **具体性**：描述越具体、格式越清晰，结果越好；但避免冗余细节。
3. **避免不明确**：直接、切中要点；指定数量、受众、风格。
4. **做什么，不说不做什么**（见§6 对抗性）。
5. **结构化**：用 `###`、分隔符、JSON/XML 提升理解。
6. **任务分解**：大任务拆成子任务，逐步构建。
7. **示例胜过描述**：Few-shot 示例对格式约束极有效。

## 3. 核心技术选型矩阵

| 技术 | 核心思想 | 适用场景 | 成本/延迟 |
|---|---|---|---|
| Zero-shot | 直接提问 | 简单分类/翻译/通用任务 | 低 |
| Few-shot | 提供示例 | 格式约束、特定风格、冷启动 | 中 |
| CoT（链式思考） | 步骤推理 | 算术、常识、符号推理 | 中 |
| Zero-shot CoT | 加"让我们逐步思考" | 无示例时的推理 | 低 |
| Auto-CoT | 自动生成示例推理链 | 大规模无标注 | 中 |
| Self-Consistency | 多路径采样取多数 | 高准确率推理 | 高 |
| Generate Knowledge | 先生成知识再作答 | 常识推理、事实性 | 中 |
| Prompt Chaining | 子任务串行 | 文档问答、多步处理 | 中 |
| ToT（思维树） | 搜索+评估思维 | 复杂规划、策略探索 | 高 |
| RAG | 检索+生成 | 知识密集、事实性、实时信息 | 中-高 |
| ReAct | 推理+行动（工具） | Agent、外部信息获取 | 高 |
| Reflexion | 语言反馈自我修正 | 决策/编程/推理迭代 | 高 |
| PAL | 生成程序交运行时执行 | 数学/日期等精确计算 | 中 |
| APE | 自动搜索最优指令 | 提示优化自动化 | 高 |
| Active-Prompt | 选不确定样本人工标注 | 提升 CoT 示例质量 | 中 |
| ART | 自动生成工具调用程序 | 工具使用任务 | 中 |
| Meta-prompting | 用 LLM 生成/优化 prompt | Prompt 工程自动化 | 中 |
| Multimodal CoT | 多模态链式推理 | 图文推理 | 高 |
| Graph Prompting | 图结构推理 | 关系/图数据 | 中 |

### 3.1 关键技术要点

**CoT**：复杂推理任务必备；与 Few-shot 结合效果更佳；"让我们逐步思考" 即可触发零样本推理。

**Self-Consistency**：采样多条推理路径，取最一致答案；适合算术/常识；成本高，仅关键路径使用。

**Prompt Chaining**：将任务拆成子任务串行，每步输出喂入下一步；提升透明度与可控性；典型：文档问答（先抽引文，再作答）。

**ToT**：维护思维树，每步评估 sure/maybe/impossible；适合需要探索/回溯的复杂任务；生产中用简化版（多专家讨论提示）。

**RAG**：LLM 参数知识静态，RAG 让其获取最新事实；是企业知识库问答的标配；配合来源引用降低幻觉。

**ReAct**：推理轨迹 + 工具调用交错；是 Agent 的基础；结合 CoT + 外部检索效果最佳。

**Reflexion**：Actor/Evaluator/Self-Reflection 三模型；从错误中学习；适合决策/编程/推理；依赖模型自评能力。

**PAL**：LLM 生成 Python 程序，交解释器执行；精确计算场景优于纯 CoT。

### 3.2 技术选择决策树

```
任务简单、无推理 → Zero-shot
需要格式/风格约束 → Few-shot
需要推理 → CoT
需要高准确率 → Self-Consistency
需要最新/私有知识 → RAG
需要外部操作 → ReAct / Agent
需要精确计算 → PAL
需要规划/探索 → ToT / Chaining
```

## 4. AI Agent 与上下文工程（企业重点）

### 4.1 Agent 三组件

- **规划**：任务分解、反思、适应（基于 LLM）
- **工具**：代码解释器、搜索、计算器、API
- **记忆**：短期（上下文缓冲）+ 长期（向量库）

### 4.2 Workflow vs Agent

| 维度 | AI Workflow | AI Agent |
|---|---|---|
| 控制流 | 预定义、显式 | 动态、自主 |
| 决策 | 硬编码 | LLM 推理 |
| 工具 | 代码编排 | 自主选择 |
| 适用 | 需求明确、可靠性优先 | 开放任务、复杂探索 |

**企业建议**：生产中优先 Workflow（可预测、可调试）；开放/探索场景用 Agent；混合架构（Workflow 路由 → Agent 执行子任务）。

### 4.3 上下文工程（Context Engineering）

上下文工程 = 架构化地设计、优化提供给 LLM 的全部上下文（system prompt、指令、工具描述、RAG、记忆、状态）。

**核心原则**
1. **消除歧义**：明确步骤、数量、格式、质量标准。
2. **期望显式化**：必做 vs 可选、输出格式、决策标准。
3. **可观测性**：记录决策、状态、工具调用、错误。
4. **迭代**：部署→观察→识别偏差→优化→测试→重复。
5. **平衡灵活与约束**：过约束→僵化；欠约束→不可预测。

**常见陷阱**
- 过约束（NEVER/ALWAYS 过多）
- 欠规格（"做些研究"）
- 忽略错误处理

**分层上下文架构**：System 层 → Task 层 → Tool 层 → Memory 层。

**企业 Checklist**
- [ ] system prompt 定义身份、能力、边界
- [ ] 工具描述含"何时用、如何用"
- [ ] 输出格式用 schema/JSON
- [ ] 错误处理指令明确
- [ ] 日志与状态追踪
- [ ] 评估指标：完成率、一致性、错误率、用户满意度、调试时间

## 5. 企业应用实战

### 5.1 案例：毕业生职位分类（Clavié et al. 2023）

任务：判断职位是否适合应届毕业生。关键发现：

- 对于不需要专业知识的任务，**Few-shot CoT 不如 Zero-shot**。
- 提示对引导推理影响巨大：基线 F1 65.6 → 优化后 91.7。
- 强制模板反而降低性能。
- 小修改影响巨大（正确指令+重复关键点最有效）。
- 给模型一个名字 +0.6 F1；正面反馈 +0.8 F1。

**企业启示**：不要盲目用 CoT；对简单分类任务，Zero-shot + 清晰指令往往更好；模板约束要权衡（strict 提升 template stickiness 但降 F1）。

### 5.2 案例：Deep Research Agent

- Search Planner：将查询拆成 2-5 个子任务（id/query/source_type/time_period/domain_focus/priority）。
- 上下文工程：结构化输出、分隔符、动态日期、RAG/记忆、状态追踪。
- 迭代优化：观察→修正→再测。

### 5.3 Function Calling 最佳实践

- 工具描述必须说明"何时用"，不仅"做什么"。
- system prompt 中再明确工具使用策略（看似重复但有效）。
- 参数用 enum 约束；描述中给示例。
- 工具失败返回信息性错误，便于 agent 恢复。
- 工具定义每次调用都占 token，保持简洁。
- 开启 intermediate steps 调试。

## 6. 风险与安全

### 6.1 对抗性提示

- **提示注入**：用户输入劫持模型输出。缓解：分隔符、警告指令、输入清洗、模型更新。
- **提示泄漏**：泄露 system prompt/示例。缓解：不把机密放 prompt；优化提示。
- **越狱**：绕过安全策略。缓解：防护栏、角色扮演检测、持续红队测试。

### 6.2 真实性（幻觉）

缓解：RAG 提供事实依据；降低 temperature；指示"不知道就说不知道"；提供已知/未知示例；要求引用来源。

### 6.3 偏见

- Few-shot 示例分布要平衡（各标签数量相近）。
- 示例顺序随机化，避免标签聚集。
- 对模型知识薄弱的任务更需谨慎。

## 7. 模型差异与选型

- **推理模型**（o3、Claude 3.7 Sonnet、Gemini 2.5 Pro）：原生 CoT，适合规划、Agent、LLM-as-Judge、Agentic RAG。
- **通用模型**：Zero-shot/Few-shot 能力强，成本低，适合简单任务。
- **选型原则**：任务复杂度 × 成本/延迟预算 × 准确率要求。
- **混合**：路由到不同模型（简单→小模型，复杂→推理模型）。

## 8. 企业级提示工程流程与模板

### 8.1 开发流程

1. **定义**：明确任务、输入输出、成功标准。
2. **基线**：Zero-shot 简单 prompt。
3. **迭代**：加上下文/示例/约束，每次只改一个变量。
4. **评估**：建立 eval 集（≥50 样本），量化指标。
5. **安全**：红队测试（注入、泄漏、越狱）。
6. **上线**：版本化 prompt，监控线上指标。
7. **持续优化**：基于线上反馈迭代。

### 8.2 System Prompt 模板

```
你是 [角色/身份]。你的任务是 [具体任务]。

约束：
- [必须做]
- [禁止做]
- 输出格式：[JSON/列表/段落]

工具使用：
- [tool_name]：何时用、如何用

错误处理：
- [失败时的行为]

当前日期：{{date}}
```

### 8.3 任务分解模板（Chaining）

```
Step 1: 从文档提取与问题相关的引文（<quotes>...</quotes>）
Step 2: 基于引文与原文生成回答
```

### 8.4 评估指标

- 任务完成率、准确率/F1
- 模板遵循率（Template Stickiness）
- 错误率、幻觉率
- 延迟、token 成本
- 用户满意度

## 9. 实战练习

1. **Zero-shot vs Few-shot**：对同一分类任务分别用 Zero-shot 和 Few-shot，对比 F1 与模板遵循率。
2. **CoT 触发**：在数学题上测试"让我们逐步思考"的提升。
3. **Self-Consistency**：对算术题采样 5 条路径，比较多数投票准确率。
4. **RAG**：用本地文档构建问答，对比有/无检索的幻觉率。
5. **ReAct**：实现一个搜索+计算 Agent，记录工具调用序列。
6. **上下文工程**：对一个 Agent 的 system prompt 做 3 轮迭代，每次记录偏差与修改。
7. **红队**：对你的 prompt 尝试注入、泄漏、越狱，记录防护效果。

## 10. 反模式清单

- ❌ 模糊指令（"做些研究"）
- ❌ 一次性复杂 prompt 不分解
- ❌ 过度约束（NEVER/ALWAYS 堆砌）
- ❌ 强制模板不权衡性能
- ❌ Few-shot 示例分布偏斜/顺序固定
- ❌ 忽略错误处理与可观测性
- ❌ 把机密放 prompt
- ❌ 不评估、不版本化
- ❌ 盲目用 CoT（简单任务反而降效）
